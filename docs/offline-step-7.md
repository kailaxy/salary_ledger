# Step 7: offline loan payments

Add → Loan pay now uses the same Review entry → Save on device flow. The review shows loan, date, amount, outstanding balance before/after, and whether a spending category/pay period will also be recorded. Cancel does not write anything. Confirm saves one durable outbox item containing both effects. The Loans screen updates repayment, installment coverage and status from the projected payment history; recent entries show one payment. An optional mirrored expense contributes once to spending/questions. Without that option, debt reduces without increasing spending.

Each loan can have one pending payment at a time. Synchronize or resolve it before adding another payment to that loan. Payments to different loans and ordinary entries can coexist in the queue. Loan creation/editing, payment editing/deletion, budget/category/settings changes remain online-only. Offline loan payments are not enabled for an older cached deployment.

## Deployment

Update Code.gs, Sync.gs, Transport.gs and Index.html; add **LoanSync.gs** as a new Apps Script file named LoanSync. Deploy a new version of the existing web app. Reliable sync must already be prepared; no new tables, headers, reordering or migration are required. The existing SYNC_JOURNAL handles these bundles. Build the signed release APK manually on main with release enabled, using the same signing secrets; install it over the existing release and refresh online. A debug artifact has a different signature. No new pairing is required for an unchanged deployment/PIN/device token. The server snapshot advertises loanSyncVersion=1 only when the module and prepared journal are available.

## Server contract and recovery

The new authenticated syncLoanPayment endpoint is add-only. It requires a permanent payment ID, mutation ID, exact loan content fingerprint, expected total paid in integer cents, and the sorted current installment fingerprints. The server checks all of these and the outstanding balance under the script lock before preparing anything. The optional expense ID is deterministic from the payment ID. Both note fields are validated; spending references are checked. An unrelated payment or changed loan/schedule produces a conflict rather than overwriting or changing the proposal. Notes on unrelated past payments do not affect the confirmed amount owed.

Before applying effects, persist the canonical request, original loan row and exact intended payment, optional expense and resulting loan row in a PREPARED journal entry. Flush each financial write and verify every intended row before the COMMITTED receipt. The receipt includes the payment, optional expense and loan row, each with its content fingerprint. On retry, return that durable receipt without adding rows or changing the installment association.

All application operations using the script lock first recover prepared loan bundles. getState now uses that lock as well, so application reads cannot expose half a bundle left by an interrupted request. Untouched intent can become a terminal conflict if its base changed. Once any financial row exists, recovery finishes the exact prepared bundle; it never discards an orphan expense or acknowledges half a payment. If a person changes a partially written target, loan or related payment/schedule directly in Sheets, recovery stops application reads/writes with SYNC_LOAN_RECOVERY_REQUIRED. Preserve the journal and pending queue. Compare the before_json/after_json audit with the affected rows, restore the original/prepared values after checking the intended payment, then retry. Do not delete the journal or clear app data to bypass recovery. Script locks cannot serialize simultaneous human spreadsheet edits; these are not database transactions. Prefer app-mediated writes. Older legacy addLoanPayment clients do not acquire this new durable request contract.

The device validates complete receipts and applies payment, optional expense, loan status and queue removal in one IndexedDB transaction. A malformed/partial receipt retains the queue. A lost reply followed by a fresh snapshot does not double-count or change the confirmed installment. Conflicts preserve the full proposal and its spending details while showing cloud-based totals. Review fetches the latest amount owed; explicit Discard pending payment rechecks the loan context online and keeps a local audit copy. It never force-applies an overpayment.

## Validation

Node tests cover contract validation, PIN/ledger restrictions, capability gating, stale confirmations, overpayment, one-pending-per-loan, optional spending/deduplication, queue restart, malformed receipts, conflicts and lost-response snapshots. Server tests inject crashes at every prepared/expense/payment/status/receipt flush boundary, with/without spending, and test recovery before reads/unrelated writes, competing payments and direct Sheet modifications. Browser tests use the actual mocked Apps Script code through hosted and origin-restricted native adapters, exercising cancel/confirm, offline reopening, lost replies, conflict review/cancel/discard and final payoff. Android build/lint/JVM checks cover compilation and the native allowlist addition. These do not replace physical phone/Keystore or live Apps Script deployment validation. Test the documented loan scenarios on the phone after deployment. LLM integration remains last.
