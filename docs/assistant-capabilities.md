# Deterministic assistant capability inventory

This is the first independently testable Phase 4 slice. Four common entry actions execute in chat; complex CRUD is reachable through the existing forms and explicit reviews. “Guided” below means navigation only, not an implemented in-chat mutation. No partial write adapters are exposed.

All data access uses the authorized local snapshot plus non-conflicting pending changes. Every write requires unlock, the same ledger identity, the appropriate existing sync capability, and an atomic IndexedDB enqueue. A local save is not a server acknowledgement. Existing handlers enforce their detailed bounds, tombstones, dependencies and linked-record invariants.

## Existing workflow validation and required form values

- Income: amount, date, existing period, SALARY/BONUS/OTHER; optional source/note. Expense: amount, date, existing spending category and period; optional note. Fund movements: the same fields with an existing FUND category and IN/OUT direction. The shared LedgerPending planner checks integer cents, amount limits, dates, available entities, fund overdrafts and sync-version support. Chat validators are a preliminary allowlist, not financial authority.
- Entry editing/deletion: exact table and record ID, fingerprint/revision, before/after review. History search is the safe identification workflow. “Last expense” never automatically selects a record in this slice. Mirrored loan expenses must be edited through the loan payment. submitLocal, editEntry, onDelete, editRecord/deleteRecord and existing reviewChange remain authoritative. No chat bulk writes.
- Category create/edit/archive/restore/delete and fund goals: Plan → openCat/submitCat → saveCategory/deleteCategory → saveOperation → LedgerOperations.plan. Required name/kind on creation, selected ID on update; optional group/archive/target/date as supported by the form. Existing linked-use checks apply.
- Budgets: Plan → savePlanLine → setBudget → saveOperation. Select existing period/category and allocation; optional apply-to-future checkbox. Amount and scoped future changes are shown in existing review.
- Loans: Loans → submitLoan/saveLoan, name/lender/principal/total/installment count/frequency/first due date on creation; the form restricts edits to preserving existing schedule/payment history. deleteLoan is restricted by linked payments. Payment: Loan pay → submitLoanLocal or editRecord/deleteRecord; selected loan, positive amount/date, optional note, explicitly selected also-spend and category/period when counted. Existing planner maintains the mirror and validates the balance/schedule.
- Pay periods: Plan displays existing periods; Settings → generatePeriods requires a year and configured pay days; review shows actual new periods. No editing arbitrary historical period boundaries is exposed because the app does not provide it.
- App settings: openSettings → saveSettings requires app name/pay days; preference controls remain device/per-ledger via AssistantPersonality. Name/pay-day changes use the existing operation review.
- Synchronization: Home displays pending, conflict and failure information. Assistant navigation never triggers a sync. Refresh/retry and resolveCloud/resolveLoanConflict/resolveOperationConflict use their existing explicit controls and reviews; cloud refresh and prepareSend enforce ledger identity/authorization. Discarding proposals retains audit copies.
- Read-only queries: all currently supported LedgerQuery operations and ranges remain unchanged, including budgets, funds, loans, comparisons, lists and English/Taglish. period.compare routes to Home, where financial questions remain available.
- Guide/help: the Guide stays in Settings; assistant help is searchable and generated directly from the allowlisted registry. Existing Home cards, Plan selection/future allocation, fund goals and loan schedules are reachable through their normal screens.

## Restricted and unsupported workflows

PIN configuration/change, lock/unlock, device pairing/revocation, initial Sheet setup, preparing reliable sync, deployment, credentials, recovery/admin and audit repair remain exclusively in the existing secure app/Sheet workflows. Help does not offer credential actions. They are not dynamic assistant handlers. Deleted financial records retain existing tombstone semantics; no restore-deleted-record command is invented. No import/export/backup feature or other absent business capability is invented. No RPC or native bridge method was added.

## Draft contract and limits

Commands use bounded explicit patterns and ledger entity choices, not general NLP. Unknown words/conditions, ambiguous entities and unsupported multi-actions fail closed or offer an existing form. Category aliases are explicit (pagkain/Food, pamasahe/Transport); lunch is a note and does not silently select a category. Archived or deleted categories are not auto-selected. Missing dates and periods require a choice; Today is explicit. The preview shows all supplied fields. Conversational yes/oo/sige cannot confirm a mutation. Cancel, Clear, replacement, background, authorization change and ledger/snapshot change discard drafts. Drafts expire after five minutes and are revalidated before confirmation. They never persist as financial records.

Direct in-chat loan payments, complex edits/deletes, plans, categories and settings are not implemented in this slice; their discoverable route opens the proven form and review flow. Their post-save messages remain those existing workflows; the new contextual reaction is currently attached to the four in-chat entry saves only. Follow-up slices can add adapters after equivalent confirmation/status tests.

The assistant also supplies an optional full-view comparison token to the shared atomic enqueue. If another tab changes the stored snapshot or pending queue after preview, that transaction aborts before writing; identical mutation-ID retries remain idempotent. This guard is additional to existing financial revision/dependency checks, not a new financial planner.
